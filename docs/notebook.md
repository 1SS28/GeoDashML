## 2026-10-17: Phase 3 search bot and curriculum

- **Surprise 7: Steam refused to launch the pinned game.** RobTop pushed a new macOS build today (public branch buildid 26002420, depot manifest 2113602821724303233, `timeupdated` 1792207383). Steam compared it with the locked `appmanifest_322170.acf` (buildid 25909607, the 2.209 build that the pin left in place), flagged "Update Required", tried to write the manifest, failed on the `uchg` flag ("Disk write failure" in `logs/content_log.txt`) and gave up on the launch (`LaunchApp failed with AppError_11` in `console_log.txt`). Running the binary straight from `Contents/MacOS` (where a `steam_appid.txt` already sits) got as far as Geode's mod graph and `SteamAPI_Init`, then exited: the Steam client refuses the session too. So the pin only holds as long as the manifest's buildid matches the public branch, which it did for one day. Fix: `scripts/refresh-steam-manifest.py` reads the current buildid and depot manifest from Steam's `appcache/appinfo.vdf` (binary VDF v29 with a string table) and writes them into the locked manifest, which keeps Steam believing the install is current without touching the game folder. Run it after every GD release, then `open steam://rungameid/322170`. Verify the binary afterwards with `dwarfdump --uuid` (arm64 UUID ABCA9EC8-...); Steam does not re-verify files on launch.
- **Surprise 8: a freshly loaded level starts only while the game window is frontmost.** After the relaunch `load_main(1)` timed out: `in_level` true, `level_id` 1, `started` false for a minute, and neither `step` nor `resetLevelFromStart` changed that (the cube sat at x 0, `on_ground` false). The bridge itself kept answering, because its commands are serviced from `mainLoop`, which runs on the CVDisplayLink thread while the window is in the background; but the start timer is scheduler-driven and cocos pauses the scheduler when the app is not active. Bringing the window to the front (`osascript`: set the process frontmost) started the level within a second; from then on resets and stepping worked in the background as before, since they do not go through the scheduler. Yesterday the window was always in front, so this never showed. Consequence: load levels with the window focused; `load_main`'s timeout error now says so.
- Search design. The bot keeps a stack of commits, each the longest surviving prefix found so far with its death tick D, and extends a commit by replaying candidate schedules that differ inside a window before D, committing the one that dies latest (`gdsearch/search.py`, README). The first live run exposed the candidate family that matters: with single toggles only (hold or release from decision j onward) the cube's move over the first spike was "hold forever", it bunny-hopped past the spike pair at 975/1005 and died at tick 1108 (x 1436), and no single toggle inside 480 ticks helped, because the fix is a release followed by a well-timed jump: a toggle pair, found after 1770-candidate enumeration started. 290 attempts to reach x 1500. Adding taps (press at j, release at j + 1) as the first family, committed at once when they die at least 16 ticks later than D, gives 65 attempts to the same point and a schedule that reads like a human's: tap, run, tap. Toggles remain the ship's move. Plain depth-first search over decisions was rejected on paper: it enumerates 2^k settings of the k decisions between the needed fix and the death before moving the fix earlier.
- **Surprise 9: the bridge cut off large replies.** The first full search died at 73% with a `JSONDecodeError` 6 MB into a reply and "client detached (send failed)" in the Geode log. A dead cube reproduces it: 20,000-, 50,000- and 100,000-tick traces come back intact (0.4 to 1.2 s), a 150,000-tick trace (6.4 MB) is cut off at about 4.9 MB. Cause: on macOS the accepted socket inherits `O_NONBLOCK` from the listener, so once the socket buffer is full `send` returns `EAGAIN` and `sendAll` treated that as a failure and dropped the client. Bridge 0.1.2 polls for `POLLOUT` and retries; the 150,000-tick trace then arrives in 0.43 s. Phase 1 and 2 never sent more than about 1 MB.
- **Surprise 10: the level never completes in lockstep; the end portal is the real end.** The 6 MB reply was the search doubling a run that stayed alive for 69,000 ticks: the player had reached the end and sat there. Reaching the end portal, at x 26424.88 (level length 26724, so 299 units short of it; the game reports 98.88%), flips `GJBaseGameLayer::m_levelEndAnimationStarted` and `PlayerObject::m_isLocked` on that physics tick and stops the player. `PlayLayer::m_hasCompletedLevel` is set by `levelComplete()`, which the end animation calls when it finishes, and that animation does not advance under the bridge: not in 240 further ticks, not in 3 s of real time with the window frontmost. So the game's own completion flag is never true while attached. Bridge 0.1.2 reports `end_anim` and `locked`; the Python client's `State.finished` is `completed or end_anim`, and GDEnv terminates with the completion bonus on `finished`. `run` also gained `stop: true`, ending a run on the tick that kills the player or reaches the end, which makes every search replay exactly as long as it needs to be and gives the completion tick for free. A from-start reset after the end works normally (attempt counter +1, release-only dies at tick 392 again).
- **Phase 3 result: Stereo Madness cleared in 3,956 attempts.** 96 commits, 0 backtracks, 164 inputs (82 taps or holds), 20,338 ticks from the reset to the end portal, 620 s of wall time at about 6 attempts/s in the first run, where each replay returned a per-tick trace of up to 1 MB; reading the death tick and position from the final state instead (no trace) gives the same 3,956 attempts in 268 s, about 15 attempts/s, which is the physics itself (a replay from the start runs until death, up to 20,000 ticks). Progress against attempts: 10.8% at 200, 40.8% at 1,600, 51.5% at 2,000, 72.9% at 2,800, 95.9% at 3,800. The search is deterministic: the second and third full runs (bridge 0.1.2 and 0.1.3, with and without traces) reproduced the same 164 inputs and the same trajectory hash. Of the 82 presses, 70 are 4-tick taps and 12 are holds between 128 and 684 ticks, all in the ship sections. The first tap is at tick 383 (the spike at x 525, inside the 328 to 382 window measured yesterday plus the 4-tick decision grid: the tap lands at 383 because 379 and 383 both clear it and the search takes the latest), then 735, 1099. The solution is `data/solutions/1.json`; its replay hash is 17022697171022085645.
- Replaying the solution through GDEnv (frame skip 4, no delay) terminates with `finished`, reward = ticks alive + 2,400, and the CSV row says `complete`; the next `reset()` starts a normal episode (`tests/test_gdsearch.py`). Level completion handling is no longer untested.
- **Surprise 11: practice mode places its own checkpoints during long episodes.** Curriculum test: from a checkpoint at x 25,178 (960 ticks before the end) the suffix of the solution completed the level, but the next `resetLevel()` respawned at x 25,892, 700 units further on, and a second run of the suffix died. The game adds a practice checkpoint every couple of seconds of play (`PlayerObject::tryPlaceCheckpoint`, driven by `updateCheckpointTest`), and `resetLevel()` respawns at the newest one. Phase 2's checkpoint test never saw it because its episodes were 416 ticks long. Bridge 0.1.3 makes `tryPlaceCheckpoint` and any `markCheckpoint` not issued by the bridge's `checkpoint` command no-ops while a client is attached, and GDEnv re-places its checkpoint if a respawn ever lands elsewhere (`stats["checkpoint_replaced"]`). With 0.1.3 the respawn after a completed episode lands exactly on our checkpoint, and the curriculum test (checkpoints 960, 2,880 and 5,760 ticks before the end, two completing episodes each, per-tick positions equal to the from-start replay shifted by the checkpoint tick) passes along with the rest of the suite: 70 tests.

## 2026-10-16 (later still): Phase 2 environment

- Wrote `gdenv/`: `GDEnv(gymnasium.Env)`, config dataclass, object table, action delay ring buffer, per-episode CSV. Design choice: one bridge `run` per decision with the due inputs at their exact tick offsets, so an action delay that is not a multiple of `frame_skip` (6 with frame skip 4) stays exact and costs no extra round trip; the per-tick trace from the same reply gives the ticks alive for the reward. The object table is sorted by hitbox left edge and sliced with `searchsorted`, 1.5 µs per call; a brute-force scan agrees on 400 random positions offline and on every step of the live tests.
- **Surprise 4: toggling practice mode livelocked the game.** Same signature as Surprise 3: main thread at 100% in `FMOD::Sound::getOpenState` holding FMOD's critical section, FMOD's thread blocked on it. Mapping the sampled offsets against the 2.2081 bindings (`mods/bridge/build/_deps/bindings-src/bindings/2.2081/GeometryDash.bro`, `m1` column): `PlayLayer::togglePracticeMode` → `FMODAudioEngine::playMusic` → `loadMusic` → `preloadMusic`. Practice mode plays its own song, and the Phase 1 fix only covered `PlayLayer::startMusic`/`prepareMusic`. It is intermittent: the first test run through the same path passed. Fix: bridge 0.1.1 makes `FMODAudioEngine::playMusic` a no-op while attached. 60 cycles of practice on / checkpoint / respawn / practice off then ran in 0.35 s.
- **Surprise 5: presses during the first three ticks after a reset are swallowed, and a held button never re-triggers.** Hold from tick 0, 1 or 2 after `resetLevelFromStart`: the cube never jumps, for 400 ticks, and dies at the first spike. Hold from tick 3 (or any later tick): jumps immediately and keeps re-jumping on landing, every 103 to 105 ticks (jump starts at 3, 106, 211, 316). After a practice checkpoint respawn only tick 0 is swallowed; presses at ticks 1 and 2 register. In both cases the first two ticks do not move the cube. Consequence for RL: an agent that chooses hold at its first decision and keeps holding is stuck forever. The env now runs 3 warm-up ticks (button released) after every reset before the first decision (`reset_warmup_ticks`, default 3, 0 restores the raw behaviour); the reset observation then shows the cube on the ground at x 1.298.
- `on_ground` is false in the state right after a reset (tick 0, no physics tick has run) and true from tick 3.
- **Surprise 6: Stereo Madness has a spike at x 0.** Object id 8, type Hazard, rect −3..3 × 99..111, sitting on the spawn point, and it does not kill the spawning cube. It is a real object in the level data, so it is in the observation at reset as a hazard at relative x 0. Harmless, but a reader of the first observation will wonder.
- The first real spike (rect x 522..528) kills the cube at x 507.62 on tick 392, where the cube's right edge (x + 15) first exceeds 522. So the exported `getObjectRect` and a 30-wide cube hitbox agree with the game's collision to within a tick, at least for this spike. The Phase 1 determinism run that died at x 508.9 died on the same spike. A single 4-tick tap clears it if pressed between ticks 328 and 382 (a 54-tick, 0.23 s window); a tap at 356 peaks at y 168.8 and lands at x 592.
- Checkpoint respawn (`resetLevel` in practice mode) restores x, y and yvel exactly to the values at `markCheckpoint`, and increments the attempt counter. `resetLevelFromStart` in practice mode keeps the checkpoint. Leaving practice mode drops it.
- Object density: 2,399 objects in Stereo Madness, 975 decoration, 4 without a role (3 secret coins, 1 Decoration-typed solid), 1,420 kept: 786 solid, 611 hazard, 19 modifier, 4 portals. A 600-unit window holds up to 124 of them (around x 25,700, the end section). Worst-case effective lookahead by slot count, i.e. how far ahead the agent is guaranteed to see:

  | `max_objects` | 24 | 32 | 40 | 48 | 64 | 80 | 96 | 128 |
  |---|---|---|---|---|---|---|---|---|
  | worst effective lookahead (units) | 70 | 102 | 132 | 190 | 270 | 342 | 450 | 600 |

  Chose 64 as the default (975-dimensional observation, at least 0.87 s of lookahead). The 19 "modifier" objects are invisible triggers (type 20, 30×30 at x 135 and so on) that `gdbridge/objects.py` maps to a role; they are in the observation. Drop them in Phase 3 if they turn out to confuse the agent.

## 2026-10-16 (later): Phase 1 bridge

- Wrote `mods/bridge`: a loopback TCP server inside the mod, newline-delimited JSON, serviced from the game's main thread with no extra threads. Protocol in `docs/bridge-protocol.md`. Python client in `gdbridge/`, managed with uv.
- **Surprise 1: `CCScheduler::update` is not a per-frame hook on macOS.** It fired every frame during the loading screen, then only sporadically at the main menu (fewer than 600 calls in 70 s), even though Geode's own main-thread queue hooks it. Counters on three candidates showed `CCDisplayLinkDirector::mainLoop` and `CCEGLView::swapBuffers` fire every frame (about 120 per second at the menu). Servicing moved to `mainLoop`. Not investigated why the scheduler hook starves; worth a note to the Geode people later.
- **Surprise 2: a freshly loaded level is not steppable for about 1 s.** `GJBaseGameLayer::m_started` flips after a real-time delay, and physics ticks before that do nothing. The client's `load_main` now waits for `started`. Resets (`resetLevel`, `resetLevelFromStart`) keep `started` true and are steppable immediately, and they increment the attempt counter.
- **Phase 1 gate passed.** `tests/test_determinism.py`: 1000 runs of 2000 ticks on Stereo Madness with a fixed 16-input schedule, one distinct 64-bit trajectory hash (7276707798765353006), 4.67 s wall time. The cube dies partway through the schedule and stays dead, which also confirms the auto-reset suppression.
- Throughput (`scripts/bench_throughput.py`, Stereo Madness, Apple Silicon):

  | mode | render on | render off |
  |---|---|---|
  | `step n=1`, one round trip per tick | 5,865 ticks/s | 14,510 ticks/s |
  | `step n=4`, one round trip per decision | 35,022 ticks/s | 57,798 ticks/s |
  | `run`, 20,000 ticks in one command | 533,898 ticks/s | 535,571 ticks/s |

  The plan's gate was 1,000 ticks/s. At frame skip 4 with rendering on, one million environment steps take about two minutes. The round trip, not the physics, is the cost: the physics alone runs at over half a million ticks per second.
- Not yet done from the original Phase 1 list: the "set practice checkpoint / reset to checkpoint" commands exist but are untested, and the geometry export has been checked only for shape, not for hitbox correctness against the game's collision. Both belong to Phase 2 when the observation builder needs them.
- **Surprise 3: resets can livelock on music.** With the test suite hammering resets, the game spun at 99% CPU forever. A `sample` of the process showed `resetLevelFromStart` → `resetLevel` → `startMusic` → `prepareMusic` → `FMODAudioEngine::setMusicTimeMS` polling `Sound::getOpenState` in a tight loop that takes FMOD's critical section on every iteration, while FMOD's own thread sat blocked on that same lock and so never finished opening the stream. Fix: while a client is attached, `PlayLayer::startMusic` and `prepareMusic` are no-ops. The offsets were mapped to names by matching the sampled addresses against the bindings' m1 addresses, which is a trick worth remembering.
- After a reset the first two ticks do not move the cube; movement starts on tick 3 at 1.29825 per tick. `m_playerSpeed` reads 0.9 at what the game calls 1x speed.
- Opening the .app directly still fails; launch with `open steam://rungameid/322170`. The main loop runs on the thread Geode labels `Main` when the window is frontmost and `CVDisplayLink` otherwise.
